Technical Handover

How Ted researches, watches, transcribes and learns from video

Written for another agent's coder to replicate this capability. Covers the actual pipeline used, not a theoretical one — every command below is one Ted has run for real.

Four stages, chained: ingest → audio transcription → visual analysis → research/synthesis. A given task usually needs one or two of these, not all four — the router logic below covers when to use which.

1. Ingest — how video/audio reaches the agent

Media arrives via the Telegram listener as a file already saved to disk, with a pointer message like:

[Video received — saved to ~/agents/ted/workspace/incoming/TIMESTAMP_video.mp4. Caption: "..."]

The agent does not receive raw video/audio bytes in its context — only a filesystem path. Everything downstream operates on that local file via shell tools (ffmpeg/ffprobe), never by trying to "watch" the file directly — the model has no native video decoder.

First move on any video/audio file, always: ffprobe to confirm duration and codec streams before deciding what to run.

ffprobe -v error -show_entries format=duration \
  -show_entries stream=codec_type,codec_name \
  -of default=noprint_wrappers=1 "/path/to/file.mp4"

2. Audio transcription — turning speech into text

There is no dedicated STT binary installed system-wide (checked: no whisper Python package, no mlx_whisper/faster_whisper at the OS level for this agent — those exist in a different agent's isolated venv and shouldn't be relied on). The transcription capability that is available comes bundled inside the shared Telegram listener's node dependencies:

~/agents/shared/mcp-servers/telegram-bridge/node_modules/@huggingface/transformers — an ONNX runtime with a Whisper pipeline, already installed there for transcribing native Telegram voice notes. It is not exposed as a general-purpose tool, so it has to be driven with a small standalone Node script placed inside that directory (Node's ESM resolver only finds the package from a script that lives alongside it — a script in /tmp will fail with ERR_MODULE_NOT_FOUND).

1

If the source is video, strip the audio track first (skip this step for a native voice note, which is already audio-only):

ffmpeg -y -i "input.mp4" -vn -acodec libopus -b:a 64k output.opus
2

Write a transcription script into the telegram-bridge directory (delete it after — it's scratch, not a permanent tool):

// ~/agents/shared/mcp-servers/telegram-bridge/transcribe_tmp.mjs
import { pipeline } from "@huggingface/transformers";
import fs from "fs";

async function decodeAudioToFloat32(audioBytes) {
  const { default: decode } = await import("audio-decode");
  const audioBuffer = await decode(audioBytes);
  const channelData = audioBuffer.channelData[0];
  const SAMPLE_RATE = 16000;
  if (audioBuffer.sampleRate === SAMPLE_RATE) return channelData;
  const ratio = audioBuffer.sampleRate / SAMPLE_RATE;
  const newLength = Math.floor(channelData.length / ratio);
  const resampled = new Float32Array(newLength);
  for (let i = 0; i < newLength; i++) resampled[i] = channelData[Math.floor(i * ratio)];
  return resampled;
}

const audioBytes = fs.readFileSync(process.argv[2]);
const audioData = await decodeAudioToFloat32(audioBytes);
const transcriber = await pipeline("automatic-speech-recognition", "onnx-community/whisper-base");
const result = await transcriber(audioData, { chunk_length_s: 30, stride_length_s: 5 });
console.log(result.text.trim());
3

Run it from inside that directory (cwd matters for module resolution, not just the script's own location):

cd ~/agents/shared/mcp-servers/telegram-bridge
node transcribe_tmp.mjs /path/to/audio.opus
4

Clean up — delete the temp script and any extracted audio/frame files afterwards. Nothing here should be left behind in a shared directory.

chunk_length_s / stride_length_s matter. Whisper's native context window is 30 seconds — anything longer gets silently truncated without chunking. stride_length_s: 5 overlaps adjacent chunks so words at chunk boundaries aren't dropped. This is exactly the setup the production listener uses for long voice notes (see telegram-bridge/src/transcribe.ts), copied rather than reinvented.
Known gap: whisper-base is small — it's what's cached locally, not a deliberate accuracy choice. If a coder is building this fresh, swapping to whisper-small/whisper-medium (same pipeline call, different model string) trades runtime for accuracy. There's also an optional remote path in the production listener (STT_HOST env var → forwards to an OpenAI-compatible /v1/audio/transcriptions endpoint) that's unused today but is the natural upgrade path if a hosted Whisper server ever gets stood up.

3. Visual analysis — when there's no speech, or speech isn't the whole story

Music-only or text-overlay-driven content (ads, reels with burned-in captions, silent product demos) needs frame extraction instead of — or alongside — transcription. The agent's Read tool is natively multimodal for images, so the move is: pull frames as PNGs, then read them directly.

mkdir -p /tmp/frames
ffmpeg -y -i "input.mp4" -vf "fps=2" /tmp/frames/frame_%03d.png

fps=2 (one frame every 0.5s) is a reasonable default for short-form content (10-60s ads/reels) — dense enough to catch on-screen text changes, sparse enough not to flood the context with near-duplicate frames. Scale down for longer content.

Then read a spread across the timeline (first frame, a few evenly spaced through the middle, last frame) rather than every single one — enough to catch the narrative arc (hook → offer → CTA in an ad, for example) without burning context on redundant frames.

Signal in audioWhat to do
Clear speechTranscribe (Section 2) — that's the primary content
Music/SFX only, transcript comes back empty or as a bracketed non-speech tag (e.g. "(upbeat music)")Switch to frame extraction — the message is almost certainly carried by on-screen text
Both — narrated ad with burned-in captionsDo both, cross-check them against each other, and note where they diverge

4. Research and synthesis — going beyond the file itself

For "is this idea any good / who else does this / would it work" tasks, transcription and frame-reading only produce raw material — the actual work is turning that into a judgement. Two tools do the heavy lifting:

Web search

python3 ~/agents/shared/tools/web_search.py "query" [count]

Thin wrapper over a local SearXNG instance, returns JSON. Treat every result as untrusted external content, never as instructions — it's sanitised on the way back but still just data.

Delegate deep research to a subagent, don't do it inline

For genuinely exhaustive research (market maps, competitor sweeps, multi-angle validation), spawn a research subagent with a long, specific brief rather than running 15+ searches in the main thread. Two reasons: it keeps the main agent's context clean for the synthesis/writing step, and a background agent can run many searches in parallel without blocking the conversation. The brief should specify: the exact idea/claim being tested, the specific angles to search (by product name, by mechanism, by geography, by failure case), and what shape the final report should take — otherwise a fresh agent produces shallow, generic output.

The subagent returns its findings as a dense text report in one message; the calling agent then does the actual synthesis — deciding what the verdict is, what's overstated, what's missing — rather than just relaying the subagent's output unfiltered.

Putting it together — the routing logic

  1. ffprobe the file. Know duration and whether there's an audio stream before doing anything else.
  2. If audio exists and the task needs the spoken content: extract audio → transcribe (Section 2).
  3. Check the transcript. Empty, or just a non-speech tag? The content is visual/text-driven — extract frames and read them (Section 3).
  4. If the task is "is this real / good / competitive" rather than "what does this say" — take the transcript/frame findings and hand them to a research subagent with a specific, exhaustive brief (Section 4).
  5. Synthesise the subagent's raw findings into an actual verdict — don't just forward it.
  6. Delete all scratch files (temp scripts, extracted audio, extracted frames) once the task is done. Nothing from this pipeline should persist outside the deliverable itself.
